## Regenerating them

Start the dashboard, then run the capture tool against it:

```bash
streamlit run dashboard/app.py --server.port 8501 &
python tools/capture_screenshots.py --port 8501
```

`make screenshots` does both, including starting and stopping the server.

## Why a capture tool rather than `chrome --screenshot`

Streamlit renders client-side over a websocket. A plain `chrome --screenshot` fires as
soon as the document loads, which is *before* the first websocket frame arrives, so it
captures the loading skeleton and nothing else — a screenshot that looks like a
deliberate design choice and is actually a timing artefact.

`tools/capture_screenshots.py` drives Chrome over the DevTools Protocol instead and
polls the DOM until the page has actually painted: no skeleton element, no "Running…"
indicator, the expected heading present, and a plausible amount of text. It then waits
for Plotly to finish before capturing.

Two details worth knowing if you modify it:

- **Navigation is by clicking the sidebar, not by deep-linking.** A direct request to
  `/explorer` reaches the server before `st.navigation` has run, so Streamlit answers
  with a "Page not found" dialog drawn over an otherwise correct page.
- **Sidebar labels and page headings differ.** The sidebar says "Benford Analysis"; the
  heading says "Benford's Law Analysis". The click target and the render check
  therefore need different strings — and because one of them contains an apostrophe,
  both are interpolated into JavaScript with `json.dumps`, not string formatting.

The tool needs no browser-automation package: `websockets` and `httpx` are already
present as Streamlit dependencies. It looks for Playwright's bundled Chromium first,
then Chrome for Testing, then a system Chrome; pass `--browser` to override.

The charts under `outputs/charts/` are a separate artefact — those are rendered by
matplotlib inside the pipeline, and are the figures the README quotes numbers from.
